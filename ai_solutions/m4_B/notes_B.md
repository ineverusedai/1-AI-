# 미션 4 — 방식 B 기록 (움직임으로만 보이는 글자, 코드 풀이)

작업 시간: 11:21 시작 ~ 11:38 종료 (UTC), 약 17분.
정답은 주어지지 않았으므로 "확신"은 1등 점수와 2등 점수의 차이(margin), 독립적인 방법끼리의 일치 여부로 판단했다.

## 0. 데이터 관찰
- 영상: 488×488, 30fps, 90프레임, 흑백(R=G=B). 검은 바탕에 지름 약 3px의 흰 점.
- 한 프레임 자체에는 글자가 전혀 안 보이고(점 밀도 균일), 단순 프레임 차분(|f1−f0|)도 모든 점이 움직이기 때문에 화면 전체가 고르게 켜져서 글자가 안 보였다. (실패 1)
- 블록 매칭(9×9 창, 정수 이동 −4..4)으로 픽셀별 최적 이동을 세어 보니 모든 영상, 모든 시점에서
  - 배경 점: 프레임당 (dy,dx)=(0,+2) 이동 (~18만 픽셀)
  - 글자 안쪽 점: (0,−2) 이동 (~1.5~2만 픽셀)
  - 그 외 이동은 1~2천 픽셀 수준의 잡음.
  즉 배경은 오른쪽, 글자 속 점은 왼쪽으로 흐른다.

## 1. 시도한 방법

### 방법 1: 단순 프레임 차분 (실패)
모든 점이 움직이므로 차분 영상에 구조가 없음. 버림.

### 방법 2: 두 움직임 가설의 잔차 차이 누적 → 글자 마스크 (채택, 핵심)
- 연속 프레임 쌍마다 e_bg = (f[t+1] − shift(f[t], 배경이동))², e_fg = (f[t+1] − shift(f[t], 글자이동))² 를 구해 전체 프레임에 걸쳐 합산.
- D = Gaussian(e_bg − e_fg, σ=2.5) 를 표준화. 글자 영역은 D가 크고 배경은 작다.
- 결과 마스크에서 굵은 산세리프 대문자/숫자 4글자가 아주 선명하게 보임(가로 방향으로 약간의 줄무늬 잡음).
- 두 이동 값은 하드코딩하지 않고, 가운데 프레임 한 쌍에서 블록 매칭 최빈값 1·2위로 매번 추정.

### 방법 3: 선택지 렌더링 + 상관계수 (채택, 판정)
- 마스크(D>1, 7×7 opening)에서 글자 덩어리의 bounding box를 찾고,
- 각 선택지를 DejaVuSans-Bold / LiberationSans-Bold / FreeSansBold 로 렌더링 → 잉크 bbox로 잘라 → 마스크 bbox 크기로 리사이즈(높이 ±6, 너비 ±12 미세 조정) → 같은 σ로 블러 → D와 정규화 상관(NCC). 글꼴/크기 조합 중 최대값이 그 선택지 점수.
- 최고 점수 선택지를 반환.

#### bbox 검출 문제와 수정 (중간 실패 → 수정)
- v1: 행/열 투영 임계값으로 bbox → q07, q29에서 화면을 가로지르는 가로 줄무늬 잡음 때문에 bbox가 커져 점수 0.35/0.20, q29는 margin 0.027로 위험, q33은 크래시.
- v2: 팽창(15×31) 후 가장 큰 연결요소만 사용 → q19(74TU)에서 7과 4 사이 간격이 커서 "4TU"만 잡혀 오답(RWK7, margin 0.056).
- v3: 가장 큰 덩어리와 같은 줄(세로 겹침 60%↑, 높이 50%↑)이고 가로 간격이 글자 높이의 0.6배 이내인 덩어리를 차례로 합침 + 글자에 붙은 얇은 가로 줄무늬는 열(column) 마스크 개수가 최댓값의 8% 미만인 열을 잘라 제거.
- v3 이후 36문제 모두 1등 점수 0.90~0.98, 2등과 큰 차이.

### 방법 4: bbox 없이 다중 스케일 템플릿 매칭 (교차검증용, 미채택)
- cv2.matchTemplate(TM_CCOEFF_NORMED)로 렌더링한 각 선택지를 높이 80~140px에서 화면 전체 탐색.
- 36문제 중 35문제가 방법 3과 일치. 불일치 1건은 q14(방법 3: 6RJX, 방법 4: GBJX, margin 0.015). q14 마스크를 직접 띄워 보니 분명히 "6RJX" (J의 아래 꼬리 때문에 고정 스케일 탐색이 어긋난 것). 방법 3이 맞다고 판단.

### 방법 5: 프레임 수 줄이기 (견고성 확인 + 속도)
- 처음 31프레임만 사용: 90프레임 결과와 36/36 일치 (v3 bbox 수정 후 q16, q24의 낮던 margin도 0.55/0.32로 회복).
- 처음 9프레임만 사용: 29/36 일치 (margin이 작아 신뢰 불가) → 영상을 어느 정도 길게 써야 함.
- 최종은 처음 60프레임 사용: 90프레임 결과와 36/36 일치, 시간 약 35% 단축.

## 3. 속도
- 단계별(대략): 디코딩 0.3~0.5s, 이동 추정 0.2s, 마스크 0.15s, 점수 0.3s.
- ffmpeg를 파이프(stdin→rawvideo gray)로 돌려 디코딩 속도를 비교하려 했으나, mp4를 stdin으로 넣으면 프레임 0개가 나와 포기(cv2 디코딩 유지). (실패)
- 처음 버전(90프레임, 이동 추정 3쌍): 평균 1.36s, 최대 2.36s(4코어, 다른 작업과 동시 실행 시) → 2초 넘을 위험.
- 최종(60프레임, 이동 추정 1쌍): 새 프로세스에서 solve() 36회 평균 0.99s, 최대 1.31s, 최소 0.80s (CPU).

## 4. 최종 방법 요약 (`solver.py`)
1. mp4 바이트를 solver 폴더 안 임시 파일에 써서 cv2로 처음 60프레임 디코딩(G 채널, 0~1), 바로 삭제.
2. 가운데 프레임 쌍에서 9×9 블록 매칭(±4px)으로 픽셀별 최적 이동 → 최빈 2개 = 배경/글자 이동.
3. 모든 연속 쌍에서 두 이동 가설의 제곱 잔차 차이를 합산, 블러·표준화 → 움직임 마스크 D.
4. 연결요소 + 같은 줄 병합 + 얇은 줄무늬 열 제거로 글자 bbox.
5. 선택지 6개 × 굵은 산세리프 3종 × 크기 미세조정 25가지 렌더링, bbox에 맞춰 NCC → 최댓값 선택지 반환.

## 5. 공정성
- 이 폴더(ai_sandbox_m4) 밖은 열거나 검색하지 않음. 예외로 `/usr/share/fonts`의 글꼴 목록·파일, 설치된 파이썬 패키지(numpy, opencv, Pillow), ffmpeg 존재 확인만 사용.
- 인터넷, 외부 AI API, OCR 서비스 사용 안 함. 정답 파일 없음/찾지 않음. submit.py는 실행하지 않음.
- 글자 판정은 전부 코드(움직임 분석 + 렌더링 상관)로 하며, 사람이 본 결과를 하드코딩하지 않음. 이동 값(±2px)도 하드코딩하지 않고 영상마다 추정.
