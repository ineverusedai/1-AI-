# 미션 1 (B) 코드로 풀기 — 작업 기록

모든 작업은 `ai_sandbox_m1/` 폴더 안에서만 했다. 학습/검증 이미지는 README 공개 사양대로
`captcha` 0.7.1 `ImageCaptcha(width=280, height=90)` (기본 글꼴, 기본 크기)로 직접 만들었다.

## 환경 확인
- CPU 4코어 (AVX-512 / AMX-bf16 지원), GPU 없음, torch 2.15 CPU.
- 캡차 1장 생성: 약 2.3ms/코어 → 4프로세스로 초당 ~1,400장.
- 기본 글꼴은 DroidSansMono(크기 42/50/56 중 랜덤). 이 글꼴은 **숫자 0 과 대문자 O 가 거의 똑같다**
  (0이 약간 좁고 길쭉한 것뿐). 캡차의 회전·찌그러뜨림(warp) 후에는 사람 눈으로도 거의 구분이 안 된다
  (`o0_compare.png` 참고: 왼쪽 열은 O0O0O, 오른쪽 열은 0O0O0 인데 구별이 어렵다). → 이게 이 과제의 핵심 난관이었다.

## 시도 기록

### 시도 1 — CRNN (CNN + 2층 양방향 GRU + CTC), fp32  → **중단 (너무 느림)**
- 입력 48x144 회색조, CNN 채널 32/64/128/192 (각 단계 conv 2개), GRU 128x2, 파라미터 159만.
- 학습 속도 실측: 배치 128 한 스텝 ~2초 = **초당 64장**. 30만장 1에폭에 80분 → 비현실적이라 200스텝에서 중단.
- 원인 분석(벤치마크): ① 합성곱 연산량 자체가 큼 ② GRU 가 스텝 시간의 ~40%.

### 속도 개선 실험 (벤치마크만)
- 채널 축소, stride-2 첫 층, channels_last, 입력 36x108 등 비교 → fp32 로는 초당 250~430장.
- CPU 가 AMX-bf16 을 지원해서 `torch.autocast(cpu, bfloat16)` + channels_last 를 써 보니 같은 모델이 **약 3배 빨라짐**.
- GRU 를 1D 합성곱(커널 5, 2층) 시퀀스 헤드로 바꾸면 GRU 비용이 사라짐.

### 시도 2 — CNN + 1D-conv 시퀀스 헤드 + CTC, bf16 학습 (본 모델, 최종 채택)
- 구조(`model.py`): conv(1→32)-pool / conv(32→64)-pool / conv(64→128)x2-pool(2,1) / conv(128→160)x2-pool(2,1)
  → 높이 3 을 펼쳐 480채널 x 36프레임 → Conv1d 1x1(256) → Conv1d k5 x2 → Conv1d 1x1(37, blank 포함). 파라미터 145만.
- 학습: `data/train1` 30만장, 6에폭, 배치 128, AdamW, OneCycle 최대 lr 2e-3, ±3px/±2px 평행이동 증강, CTC 손실.
- 속도: 단독 실행 시 초당 ~370장(스텝 0.3~0.4초). 학습 총 9,060초(약 2시간 31분, 이 중 약 25분은 O/0 실험을 위해 일시정지, 다른 작업과 CPU를 나눠 쓴 구간이 있어 느려짐).
- `data/val`(1만장) 에폭별 5글자 전체 정답률:

| 에폭 | 전체 | 글자별 |
|---|---|---|
| 0 | 92.37% | 98.33% |
| 1 | 97.68% | 99.49% |
| 2 | 98.39% | 99.65% |
| 3 | 98.26% | 99.65% |
| 4 | 99.16% | 99.83% |
| 5 (최종) | **99.25%** | 99.85% |

- 최종 에폭 오류 75건 중 **67건이 O↔0 혼동**(O→0 40, 0→O 27), 나머지는 8건뿐(B→E, R→P 등 1건씩).
  에폭 0 때는 O→0 364건, 7→1 107건, B→8 47건 등 다양했는데 학습이 진행되며 O/0 만 남았다.
- 본 모델만으로 O/0 판별 정확도: 에폭1 91.8% → 최종 96.4% (`data/spec_val` 기준).

### 시도 3 — O/0 전문 분류기 (1차, 본 모델 에폭1 정렬 사용)
- 아이디어: 48x144 로 줄이면 O 와 0 의 미세한 차이(폭/획 두께 비율)가 뭉개진다. 본 모델의 CTC 탐욕 경로에서
  각 글자의 중심 프레임을 구해, **원본 해상도(90x280)** 회색조 이미지에서 그 글자 주변 90x96 조각을 잘라
  작은 CNN(conv 24/48/64x2/96x2 + GAP, 이진분류)으로 O 인지 0 인지 다시 판정한다.
- 데이터: `spec_train` 12만장 (정렬 결과 길이≠5 인 193장 제외), 4에폭, bf16.
- `spec_val` O/0 정확도: 에폭0 91.1% → 에폭1 82.5%(불안정) → 에폭2 98.2% → 에폭3 **98.5%** (본 모델 에폭1 은 91.8%).
- 본 모델(에폭1)+전문분류기 조합으로 dev 1,000장: 99.2% (본 모델 에폭1 단독 97.7%). → 효과 확인.
- 실수: 본 학습과 동시에 돌렸더니 OpenMP 스레드가 서로 경쟁해서 둘 다 극도로 느려짐(본 학습 200스텝에 12분+).
  본 학습을 SIGSTOP 으로 일시정지하고 전문분류기만 돌린 뒤 SIGCONT 로 재개했다.

### 시도 4 — O/0 전문 분류기 (2차, 최종 본 모델 정렬 + 데이터 24만장) → 최종 채택
- 최종 본 모델로 다시 정렬해서 조각 생성: `spec_train`+`spec_train2` 24만장 중 239,949개 (정렬 17분).
- 같은 구조, 4에폭, 배치 128, lr 2e-3, bf16, 4스레드 단독 (초당 ~620장, 학습 약 27분).
- `spec_val` O/0 정확도: 94.4% → 87.6% → 98.8% → **99.14%** (같은 데이터에서 본 모델 단독은 96.4%).
- solver(본 모델 + 전문분류기) dev 5,000장: **99.82%** (오류 9건, 그중 O/0 6건).

### 시도 5 — 전문분류기 시험시 증강(TTA) 비교 (dev 5,000장으로만 선택)
자르는 중심을 CTC 프레임 단위로 조금 옮긴 조각들의 로짓을 평균.

| 이동량(프레임, 1프레임≈7.8px) | dev 전체 정답률 | O/0 오류 | 평균 ms |
|---|---|---|---|
| 0 (없음) | 99.82% | 6 | 11.0 |
| -0.25, 0, 0.25 | 99.88% | 3 | 12.1 |
| **-0.5, 0, 0.5 (채택)** | **99.92%** | 1 | 12.2 |
| -1, 0, 1 | 99.86% | 4 | 12.2 |
| -1, -0.5, 0, 0.5, 1 | 99.90% | 2 | 14.3 |

→ 3장 평균(±0.5프레임)을 기본값으로 정함. (dev 에서 차이가 몇 건 수준이라 잡음도 섞여 있음 — 최종 검증에서 O/0 오류는 dev 보다 많이 나왔다.)

## 최종 구성 (`solver.py`)
1. PNG 바이트 → RGB → 회색조. 48x144 로 줄여 본 모델(CNN+1D conv+CTC, `model_final.pt`, 145만 파라미터)에 넣음.
2. CTC 탐욕 디코딩. 결과가 5글자가 아니면 "정확히 5글자" 제약 Viterbi 디코딩으로 대체.
3. 결과 중 O 또는 0 인 자리는, 원본 해상도 회색조에서 그 글자 중심 90x96 조각 3장(±0.5프레임 이동)을 잘라
   O/0 전문분류기(`spec_final.pt`)의 로짓 평균으로 다시 판정.
4. 모델 두 개는 import 시 한 번만 로드. torch 스레드 1개 (환경변수 SOLVER_THREADS 로 변경 가능).

## 최종 검증 (`data/test_final.pkl`, 시드 4242, 10,000장, 학습·모델선택에 전혀 안 쓴 세트)
`eval_solver.py` 가 `import solver` 후 `solver.solve(png_bytes)` 로 한 장씩 돌림 (결과: `final_eval.txt`).

- **5글자 전체 정답률: 99.72% (9,972 / 10,000)**
- **글자별 정답률: 99.944%**
- 오류 28건 중 21건이 O↔0 (O→0 15, 0→O 6). 나머지 7건: B→3 2, Z→2, P→F, V→X, 1→2, B→8 각 1.
  → 이 세트의 O/0 글자 약 1,640개 기준 O/0 판정 정확도 약 98.7%.
- solve() 1장당 시간 (CPU 1스레드): **평균 12.35ms**, p99 30.2ms, 최대 42.7ms, 첫 호출 28.7ms.
- examples/ 8장: **8/8 정답**.
- 10문제 연속 정답 확률 추정: 0.9972^10 ≈ 97.2%.

### 일관성 확인
- 같은 test_final 을 학습 파이프라인 방식(`gen.preprocess` → npy → 본 모델 탐욕 디코딩, `eval_val.py`)으로 재면 99.14% (길이≠5 가 4건),
  solver 에서 전문분류기만 끄고(`SOLVER_NO_SPEC=1`) 재면 99.17% (`nospec_eval.txt`). 차이 3건은 solver 의 5글자 제약 Viterbi 가
  길이 오류 4건 중 3건을 고친 것 → 전처리가 학습 때와 동일함을 확인.
- 즉 99.17%(본 모델만) → 99.72%(전문분류기+TTA 추가) 로 O/0 보강 효과가 확인됨.

## 시간
- 데이터 생성: 본 학습 30만장 ~4분, 전문분류기용 24만장 ~10분, 검증 세트들 ~1분.
- 본 모델 학습: 9,060초 벽시계(약 2시간 31분; 그중 ~22분은 일시정지, 다른 작업과 CPU 경쟁으로 느려진 구간 포함. 단독이면 약 75분 분량).
- 전문분류기 1차 2,469초(정렬 포함), 2차 2,652초(정렬 17분 포함).
- 첫 학습 시작(11:28)부터 마지막 학습 종료(14:44)까지 약 3시간 16분.

## 남은 한계 / 더 해볼 것
- 남은 오류의 75%가 O↔0. 이 글꼴에서는 원리적으로 애매한 경우가 있어 100%는 어렵다고 본다.
  더 올리려면 전문분류기 데이터·에폭 증가, 여러 개 앙상블, 본 모델 로짓과 결합 등을 시도해 볼 수 있다.
- 시간 제약 때문에 본 모델은 6에폭 1회만 학습했다 (에폭 4→5 에서도 오르고 있었음).
